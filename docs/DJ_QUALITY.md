# Качество DJ-разметки и дополнительная проверка

Это план дополнительного прохода, не описание уже подключённого облачного LLM.
Массовый полный анализ и его запуск на Mac описываются отдельно.

Один короткий фрагмент позволяет песне участвовать в ремиксе один раз. Два–три
различных фрагмента позволяют возвращаться к ней. Число потоков ускоряет анализ,
но не превращает неуверенную границу слова в надёжную.

## Что ограничивает текущий подбор

Для выхода нужна пауза между двумя уверенно распознанными словами длиной хотя
бы 0,9 секунды: по 0,2 секунды запаса около слов и минимум 0,5 секунды затухания.
Для входа достаточно паузы 0,5 секунды. Отсутствие распознавания не считается
паузой. Эти правила намеренно консервативны, но песни с плотным вокалом могут
не получить ни одного короткого фрагмента даже после полного просмотра.

LLM, которому передали только название, график общей громкости или неточную
транскрипцию, не может подтвердить отсутствие обрезанного слога. Громкий удар
барабана и вокал также нельзя надёжно отличить по одной общей RMS-кривой.

## Рекомендуемый порядок

1. Полный локальный проход песни, повторное использование кеша и сохранение
   нескольких разных вариантов. Не ограничивать поиск тремя короткими окнами.
2. Только для неудачных песен — более точная модель распознавания и/или
   фонетическое выравнивание слов с исходным аудио. Сравнить качество на небольшом
   наборе сложных песен, прежде чем обрабатывать им всю библиотеку.
3. Аудио-LLM может предложить музыкально осмысленные участки: припев, завершённую
   фразу, инструментальный кусок. Его результат — кандидат, а не окончательное
   подтверждение точной границы.
4. Кандидаты уточняются локально по аудио, словам и сетке ударов. При сомнении
   они остаются на дополнительной проверке; ранее готовые варианты сохраняются.

Для такой проверки достаточно коротких участков с контекстом около границ,
но LLM, выбирающему саму музыкальную секцию, нужен более широкий контекст песни.
Поддержка JSON или уверенный ответ модели сами по себе не доказывают точность
таймкода. Обычный DJ может сохранить полный трек как запасной вариант; это не
нужно выдавать за готовый короткий ремикс.

## Доступные технические варианты

[WhisperX](https://github.com/m-bain/whisperX) добавляет фонетическое выравнивание
к распознаванию; поддерживает CPU и Mac с int8. Нужна модель выравнивания для
языка песни. Это дополнительная точность, но не гарантия для пения и наложенного
вокала. Более крупные ASR-модели требуют больше памяти.

[faster-whisper](https://github.com/SYSTRAN/faster-whisper) работает на CPU с int8.
В опубликованном авторами CPU-замере small требовал около 1,48 ГБ RAM; это замер
на другой записи и машине, а не прогноз нашей нагрузки. Поэтому small/medium
не следует молча запускать в прежнем серверном лимите 1 ГБ или сразу во всех
параллельных процессах.

[Gemini Audio API](https://ai.google.dev/gemini-api/docs/audio) принимает аудио,
распознаёт также неречевые звуки и допускает запросы с таймкодами. Это возможный
облачный проверяющий, но для него нужны API-ключ, выбранная модель и контроль
расходов. Для предварительной оценки документация задаёт 32 входных токена на
секунду аудио. Сначала нужен небольшой пилот с прослушиванием результата; цену
в деньгах следует считать по выбранной модели и фактическому объёму, а не
переносить с другой модели. Облачный проверяющий пока не подключён.

В текущем faster-whisper на Mac используется CPU: [CTranslate2](https://opennmt.net/CTranslate2/hardware_support.html)
поддерживает ARM64, но его обычный GPU-путь рассчитан на NVIDIA. Для последующего
ускорения на Apple Silicon можно отдельно оценить [whisper.cpp](https://github.com/ggml-org/whisper.cpp),
который использует Metal/Core ML. Его словные таймкоды отмечены авторами как
экспериментальные; смена движка требует сравнения границ, а не только скорости.
